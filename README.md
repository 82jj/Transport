# Transport — four independent deployable projects

## الفصل الفعلي (0.3.0)

هذا المستودع يحتفظ بأربعة مشاريع مستقلة تمامًا في البناء والتشغيل، وليس تطبيقًا يغيّر واجهته بـ `APP_MODE`:

| المشروع | مجلد البناء الوحيد | رابط الواجهة |
| --- | --- | --- |
| المستخدم | `apps/user` | https://transport-user-isolated-production.up.railway.app |
| الكابتن | `apps/captain` | https://transport-captain-isolated-production.up.railway.app |
| لوحة الإدارة | `apps/admin` | https://transport-admin-isolated-production.up.railway.app |
| API | `apps/api` | خدمة خلفية فقط، بدون واجهات |

لكل مشروع package.json وDockerfile وملفات تشغيل خاصة. لا تُنسخ ملفات أي واجهة أخرى إلى صورة Docker. يمكن نقل أي مجلد إلى مستودع مستقل دون تغيير كوده؛ بقاؤها في مستودع واحد لإدارة الإصدارات فقط. تنقل الواجهات طلبات API المسموحة إلى الخدمة الخلفية نفسها عبر الشبكة الداخلية، ولا تتصل بروابط بعضها ولا تحتوي أزرارًا للتبديل بينها. `APP_MODE` مهمل وغير مستخدم. ملف التشغيل في جذر المستودع يعيد 410 بدل الواجهة الجامعة القديمة.

## الإعداد

في Railway عيّن Root Directory لكل خدمة إلى `/apps/user` أو `/apps/captain` أو `/apps/admin` أو `/apps/api`. ملف إعداد Railway مساره مطلق من جذر المستودع مثل `/apps/user/railway.json`. أمر البدء `node server.js` وفحص الصحة `/healthz`.

الواجهات تحتاج `API_ORIGIN` يشير إلى عنوان خدمة API الداخلية مع المنفذ، و`PUBLIC_ORIGIN` يساوي رابط الواجهة نفسها. لا توجد عناوين الكابتن أو الإدارة داخل تطبيق المستخدم. API يحتاج `DATA_DIR=/data` على Volume دائم؛ البيانات والحسابات والجلسات تحفظ في SQLite، وليس مصفوفة مستقلة داخل كل واجهة. لا يفتح API صفحات HTML ولا ملفات الواجهات.

تهيئة أول حساب إدارة تكون بمتغيري `ADMIN_EMAIL` و`ADMIN_PASSWORD` (16 حرفًا على الأقل) في خدمة API فقط. لا توجد كلمة مرور افتراضية، ولا تسجيل إدارة عام. لا تضع كلمات المرور في المستودع. الحساب يُنشأ مرة واحدة؛ تعديل المتغير لا يعيد تعيين كلمة مرور حساب قائم. تسجيل المستخدم والكابتن منفصل، والكابتن ينتظر موافقة الإدارة. الكوكيز خاصة بالنطاق وبالدور، HttpOnly وSameSite=Strict وSecure في الإنتاج.

## التحقق

`npm run check` و`npm test` يفحصان التطبيقات الثلاثة وخدمة API فعليًا عبر HTTP. الاختبارات تشمل منع ملفات الواجهات الأخرى، منع تبديل الواجهة باستعلام URL أو APP_MODE، عزل الجلسات والصلاحيات، مشاركة الطلب بين الواجهات، موافقة الكابتن، قبول واحد للطلب، انتقالات الحالة، وحفظ البيانات بعد إعادة تشغيل API.

CI يبني كل Dockerfile من مجلده فقط. فحص `live-isolation` لا يكتفي بـ SUCCESS في Railway: يقارن HTML وJS وCSS والـmanifest على الروابط العامة مع ملفات commit الحالي بالـSHA-256، ويختبر 404 للمسارات الأجنبية و401 للبيانات المحمية. لا ينشئ بيانات اختبار في الإنتاج. النشر الحي لا يعتبر متحققًا حتى ينجح هذا الفحص على الرأس المنشور.

## حدود هذه النسخة

نسخة معاينة وليست تشغيلًا تجاريًا مكتملًا. أسعار الخدمات موروثة من النموذج التجريبي وغير معتمدة للتشغيل؛ المسافة مدخلة يدويًا. الخرائط وGPS واختيار أقرب نقطة وصول وتتبع المركبة والدفع وإثبات التسليم والتحقق من المستندات والإشعارات ليست موصولة بعد. إسناد الكباتن حسب نوع المركبة والقرب يحتاج إكمالًا. لا تعرض الواجهات أرقام كباتن أو تقييمات أو إيرادات أو شكاوى وهمية. جميع الطلبات الحالية موسومة كتجريبية. كلمات مرور الاختبارات مخصصة للبيئة المؤقتة في CI ولا تُستخدم في الإنتاج.

المشروع مستقل عن SMT وعن مشروع توصيل الركاب.
